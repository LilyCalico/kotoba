# 入力の分類と質問への回答を Gemini の structured output で行う

## ステータス

採用

## コンテキスト

プレイヤーは 1 つの入力欄から、秘密の単語についての質問と、単語そのものの解答の両方を送る（`docs/specifications/game.md`）。api は入力ごとに次を決める必要がある。

- 質問か、解答か、対応外の言語（日本語・英語・スウェーデン語以外）か
- 質問なら、5 値（はい / いいえ / どちらとも言えない / それは関係ない / 質問の形にしてね）のどれを返すか

満たすべき要件は次のとおり。

1. 応答は 5 値と対応外言語の案内だけにし、秘密の単語や定義の断片が応答に漏れない
2. 同じゲームの中で、回答が前の回答と矛盾しない
3. AI が失敗しても、ゲームを壊さずに「もう一度送ってね」で再送できる
4. 1 入力あたりの費用と待ち時間を小さく保つ。モデルは Gemini の Flash 系の安価なものを使う
5. CI の E2E は Gemini のキーなしで、決定的に流れる

## 決定

### 判定の流れ

| 段 | 判定 | AI |
| --- | --- | --- |
| 1 | `isAcceptedAnswer` の正規化マッチで正解なら、クリアにする | 呼ばない |
| 2 | 外れた入力を Gemini に渡し、`kind`（`question` / `answer` / `unsupported_language`）と、質問なら `verdict`（5 値）を返させる | 1 回（失敗時は再試行を含めて最大 2 回） |

`answer` と分類された入力は誤答にする。

### AI の口

`GamesService` は `InputJudge` インターフェースだけを知り、Gemini の実装（`GeminiInputJudge`）はその裏に置く。

| 項目 | 決めたこと |
| --- | --- |
| 出力 | structured output（`responseJsonSchema`）で `{ kind, verdict }` の enum だけを返させ、応答を zod で検証する |
| プロンプト | システム指示に、分類の規則・秘密の単語の情報（綴り・品詞・定義・直訳・補足・例文）・そのゲームの全 Q&A 履歴を置く。プレイヤーの入力は本文にだけ置き、指示として扱わないことを明示する |
| 生成 | `temperature: 0` |
| モデル | 既定は `gemini-3.5-flash-lite`。`GEMINI_MODEL` で差し替える |
| 障害時 | 1 回の呼び出しは 10 秒で打ち切る。エラー・タイムアウト・スキーマに合わない応答は 1 回だけ再試行し、2 回とも失敗したら `ai_unavailable`（503）。SDK 側の自動リトライは切る |
| キーがない | 起動を止めず、警告を出して `ai_unavailable` を返す実装を差し込む |
| E2E | Gemini の接続先（`GEMINI_BASE_URL`）を、決まった規則で応答するスタブサーバーへ向ける |

## 検討した選択肢

### 正規化マッチを AI の後に置く

AI に分類させてから、解答と分類された入力だけを正規化マッチにかける。分類と判定の役割分担はきれいになる。

一方で、正解の入力にも AI の費用と待ち時間がかかり、AI が正解を質問と取り違えるとクリアできない。正規化マッチを先に置けば、正解はコードだけで確実に決まる。

### 回答を自由文で返させ、enum に読み替える

モデルに「Yes, it is.」のような文で答えさせ、コードで 5 値に読み替える。

自由文は単語や定義の断片を含みうる（要件 1）。読み替えの規則もモデルの言い回しに追従し続ける必要がある。structured output で enum に縛れば、応答に載りうる値が出力の型で決まる。

### 履歴を要約して渡す

長いゲームでプロンプトが伸びないよう、過去の Q&A を要約して渡す。

要約の段で事実が落ちると、要件 2 の矛盾防止が崩れる。入力は 200 字以内で、1 ゲームの入力数も人が打てる範囲に収まるため、全履歴をそのまま渡しても費用は小さい。

### キーがないときに簡易ルールで代用する

キーがなければ、疑問符などで質問を見分け、常に「どちらとも言えない」を返す。手元と E2E がキーなしで動く。

本番でキーを設定し忘れても静かに「どちらとも言えない」を返し続け、障害に気づけない。

### キーがないと起動しない

設定漏れには確実に気づける。一方で、CI の E2E とキーを持たない手元で api が立たなくなる。E2E のためには結局スタブが要る。

### E2E で AI を迂回するフラグを持つ

環境変数でスタブの判定に切り替える。スタブサーバーが要らない。

本番に AI を迂回する経路が載り、誤って有効になると気づきにくい。SDK の呼び出しと応答の検証も E2E で通らない。接続先だけを差し替えるスタブなら、本番と同じコードを通る。

## 影響

- 応答に載りうる値は、structured output のスキーマと zod の検証で 5 値と対応外言語に限られる
- 正解はコードの正規化マッチで決まり、AI の判断に左右されない。スペルミスや音写ゆれの救済は別の段（#29）で足す
- 全履歴をプロンプトに入れるため、入力ごとの入力トークンはゲームが進むほど増える
- Gemini の障害は `ai_unavailable` として画面に届き、同じ入力を再送できる
- E2E は分類の精度を見ない。精度とプロンプトインジェクション耐性は eval セット（#31）で測る

## 見直しの条件

- eval で Flash-Lite の精度が足りないとわかった場合。`GEMINI_MODEL` で上位のモデルに替え、費用と待ち時間を比べる
- 1 ゲームの入力数が増え、全履歴のプロンプトが費用か待ち時間の問題になった場合
- 10 秒の打ち切りと 1 回の再試行で、Vercel の関数の時間や体感の待ち時間が許容できなくなった場合
