# 0003. 進行中ゲームを GameStore の裏で保持し、デプロイ前に共有ストアへ差し替える

## ステータス

採用（2026-09-28）

## コンテキスト

ゲームセッション API（`docs/specifications/api.md`）は、プレイ中のゲームごとに次の状態を持つ。

| 状態 | 使い道 |
| --- | --- |
| 単語の id | 解答の判定、ヒントと結果の組み立て |
| `locale` | 設問・ヒント・定義を返す言語 |
| 開示済みヒントの数 | ヒント番号の検証 |
| Q&A 履歴 | AI の判定に全履歴を渡し、回答の一貫性を保つ（#28） |
| 終了状態と結果 | 終了後の操作の拒否、ギブアップの再送への同じ結果の返却 |

`docs/specifications/game.md` の AI 設計は「秘密の単語・Q&A 履歴はサーバーのみが保持し、クライアントには一切送らない」と定める。この状態はサーバー側に置く必要がある。

一方でデプロイ先は Vercel（Fluid Compute）である。関数のインスタンスは負荷に応じて複数立ち、使われないインスタンスは停止する。インスタンスのメモリは互いに共有されない。

満たすべき要件は 2 つある。

1. **状態をサーバーだけが持つ** — クライアントに単語や履歴を渡さない
2. **どのインスタンスに届いても同じゲームを続けられる** — 開始したインスタンスと次の入力を受けるインスタンスが異なっても、ゲームが見つかる

2 は Vercel にデプロイした時点で初めて必要になる。ローカル開発と CI は単一のプロセスで動く。

## 決定

進行中ゲームの読み書きを `GameStore` インターフェースの裏に隠す。API のほかのコード（コントローラー・判定・ヒント）は `GameStore` だけを知り、保存先を知らない。

保存先は段階的に入れる。

| 段階 | 保存先 | Issue |
| --- | --- | --- |
| ゲームセッション API の実装 | メモリ内（プロセス内の `Map`） | #24 |
| Vercel へのデプロイの前 | 複数のインスタンスで共有できるストア（Supabase の PostgreSQL か Redis） | #63 |

最後の操作から 1 時間経ったゲームは破棄し、`game_not_found` を返す。メモリ内の実装ではプロセス内で期限を管理し、共有ストアでは TTL を使う。

メモリ内の実装は、共有ストアへ差し替えたあともユニットテスト用に残す。

## 検討した選択肢

### 最初から DB に保持する

要件を 2 つとも最初から満たし、あとで差し替える手間がない。

ただし DB の基盤（#32 の Prisma + Supabase）が整うまでゲームセッション API に着手できない。API の振る舞い（判定・ヒント・エラー）を固める作業と、保存先を整える作業は独立しており、前者を後者の完了まで止める理由がない。

### 暗号化したトークンで状態をクライアントに持たせる

ゲームの状態を暗号化してクライアントに渡し、リクエストのたびに送り返させる。サーバーはストアを持たずに済み、どのインスタンスでも復号すれば続きを処理できる。

要件 1 から外れる。暗号化していても、秘密の単語と Q&A 履歴がクライアントの手元に置かれる。さらに Q&A 履歴は入力のたびに伸びるため、トークンもリクエストのたびに肥大する。クライアントが古いトークンを送り直せば、開示したヒントの数などを巻き戻せる点も扱いにくい。

### GameStore の裏でメモリ内から始め、デプロイ前に共有ストアへ差し替える（採用）

API の実装をすぐに始められ、保存先の選定は必要になる時点（デプロイの前）まで遅らせられる。差し替えは `GameStore` の実装を入れ替えるだけで、API のほかのコードに波及しない。

## 影響

### 得たもの

- ゲームセッション API の実装（#24）を、DB の基盤（#32）を待たずに始められる
- 保存先の選定を、Vercel Marketplace の選択肢（Supabase / Upstash Redis など）を比べられる時点まで遅らせられる
- ユニットテストがメモリ内の実装で完結し、外部のストアを要さない

### 引き受けたコスト

- メモリ内の段階では、プロセスが再起動すると進行中のゲームがすべて消える。ローカル開発ではファイル変更による API の再起動でゲームが `game_not_found` になる
- メモリ内の実装のまま Vercel にデプロイすると、別のインスタンスに届いた入力が `game_not_found` になる。#27（Vercel へのプレビューデプロイ）は #63 の後に行う必要がある

## 見直しの条件

- 認証と戦績の保存（`game.md`「実装予定の機能」）を入れるとき。進行中ゲームも DB に置き、戦績と同じストアで扱うかを再検討する
- 共有ストアの読み書きが、入力の応答時間の大半を占めるようになったとき
