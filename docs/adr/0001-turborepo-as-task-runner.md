# 0001. Turborepo をタスクランナーとして採用する

## ステータス

採用（2026-09-13）

## コンテキスト

kotoba は 3 つのワークスペースからなる pnpm モノレポである。

| ワークスペース | 中身 | ビルド |
| --- | --- | --- |
| `apps/web` | Next.js（App Router） | `next build` |
| `apps/api` | NestJS（REST） | `nest build` |
| `packages/shared` | 型・zod スキーマ | `tsc` |

パッケージを分けているのは構成上の必然による。NestJS は `experimentalDecorators` と `emitDecoratorMetadata` を有効にした tsconfig を要求し、DI はコンパイル後に残る型メタデータに依存する。Next.js は Turbopack / SWC の経路でビルドされ、この設定を共有できない。TypeScript のバージョンも `apps/api` が 6 系、`apps/web` が 5 系に分かれている。

この構成が、タスク実行に 2 つの要件を課す。

1. **順序の保証** — `packages/shared` は `tsc` で `dist` を生成し、`main` と `types` がその成果物を指す。`apps/web` と `apps/api` のビルドより前に、必ず `packages/shared` のビルドが完了している必要がある。この前提が崩れると、型解決は通るのに実行時に解決できない状態になる。
2. **実行時間の抑制** — 現状のフルビルドは約 4 秒で、実行時間は問題になっていない。ただし `docs/specifications/non-functional-requirements.md` が定める CI（lint / test / deploy、Playwright による E2E、AI の eval セット）が揃った段階では、CI の実行時間が開発サイクルを律速する。変更のないパッケージのタスクを飛ばす手段が必要になる。

## 決定

Turborepo をタスクランナーとして採用する。

ルートの `package.json` の scripts はすべて `turbo run` への転送とし、タスクの定義は `turbo.json` に集約する。

**順序は宣言しない。** `dependsOn: ["^build"]` の `^` は「自身が依存するワークスペースの同名タスク」を指す。Turborepo は各 `package.json` の依存（`"@kotoba/shared": "workspace:*"`）からグラフを導出するため、`packages/shared` を先に、という記述はどこにも現れない。ワークスペースを追加しても設定の変更を要さない。

**キャッシュ対象は `outputs` で明示する。** `.next/**` と `dist/**` を対象とし、`.next/cache/**` は除外する。Next.js の内部キャッシュを取り込むとキャッシュエントリが肥大するためである。

**開発サーバーは別扱いとする。** `dev` タスクは `cache: false` かつ `persistent: true` とする。終了しないタスクであることを宣言しないと、Turborepo が後続タスクの実行を待ち続ける。

キャッシュはローカルのみとし、リモートキャッシュは接続しない。

## 検討した選択肢

### pnpm の再帰実行のみ（`pnpm -r`）

追加の依存を持たない。`pnpm -r build` はワークスペースの依存グラフをトポロジカル順で実行するため、**順序の保証という要件は単体で満たす**。実測でも `packages/shared` → `apps/web` / `apps/api` の順に実行される。

満たさないのはキャッシュである。入力が変わっていないパッケージも毎回ビルドとテストを実行する。パッケージ単位・タスク単位で結果を再利用する仕組みがないため、CI の実行時間が伸びたときに打てる手が「並列度を上げる」以外に残らない。

### Nx

プロジェクトグラフ、影響範囲の検出、コードジェネレーターを備え、Turborepo の上位互換にあたる機能を持つ。

3 ワークスペースの規模に対して、設定量と習得すべき概念が見合わない。プラグインごとの実行器（executor）の抽象が挟まるため、`nest build` や `next build` をそのまま呼ぶ構成と比べて、トラブル時に追うべき層が増える。

### Turborepo（採用）

`turbo.json` 1 ファイルで両方の要件を満たす。各ワークスペースの `package.json` の scripts をそのまま呼ぶ設計のため、Turborepo を外しても各パッケージは単体で動作する。

ホスティング先が Vercel であり、必要になった時点でリモートキャッシュへ移行できる点も評価した。

## 影響

### 得たもの

- 依存順序が設定ではなくワークスペースの依存関係から導出される。ワークスペース追加時に順序定義の更新が要らない
- フルビルド約 4.1 秒に対し、入力が変わらない場合の再実行は約 26 ミリ秒になる。内訳は `packages/shared` 0.8 秒、`apps/api` 1.6 秒、`apps/web` 3.3 秒の削減
- `turbo run build --dry` でタスクグラフとキャッシュの判定結果を検査できる

### 引き受けたコスト

- ルートの依存が 1 つ増える。バージョン更新の対象になる
- タスクを追加するたびに `turbo.json` への登録が要る。登録を忘れたタスクはキャッシュも順序解決も受けない
- `outputs` の指定漏れは、キャッシュヒット時に成果物が復元されないという形で表面化する。ビルドが成功したのに出力が存在しない、という分かりにくい症状になる
- 現時点での実効的な利益は順序解決に限られる。キャッシュの価値はテストと eval が揃うまで現れない

## 見直しの条件

- **リモートキャッシュへ移行する**: CI の実行時間が開発サイクルの妨げになった時点。Vercel のリモートキャッシュを接続し、CI とローカルでキャッシュを共有する
- **Turborepo を外す**: `packages/shared` が不要になるなどしてワークスペースが 2 つ以下に減り、かつ CI の実行時間が問題にならない状態が続いた場合。`pnpm -r` へ戻す。各ワークスペースの scripts は Turborepo に依存していないため、`turbo.json` とルートの scripts の書き換えのみで済む
- **Nx を再検討する**: ワークスペースが 10 を超え、影響範囲検出やコード生成の必要が生じた場合
