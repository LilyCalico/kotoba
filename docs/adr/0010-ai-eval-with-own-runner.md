# AI の判定の eval を、判定の実装を直接呼ぶ自前のランナーで流す

## ステータス

採用

## コンテキスト

入力の分類・質問への 5 値の回答・解答の救済判定は、Gemini の判定に頼る（ADR 0008・ADR 0009）。プロンプトやモデルを変えたときに精度が落ちていないかと、プロンプトインジェクションに耐えるかを、期待値つきのケースで測る必要がある（`docs/specifications/non-functional-requirements.md`「AI 品質」）。

満たすべき要件は次のとおり。

1. 本番と同じプロンプト・structured output のスキーマ・応答の検証を通して測る
2. 手元で 1 コマンドで流せ、ケースごとの成否がわかる
3. CI では、判定に関わる PR と毎晩だけ流す。実際の Gemini を呼ぶ費用と、AI の揺れによる失敗を全 PR に乗せない
4. Gemini は無料枠で使う。1 分あたり・1 日あたりの上限の中で全件を流しきる
5. AI の判定は呼ぶたびに少し揺れる。1 件の揺れで落ちず、精度の低下は見逃さない

## 決定

`apps/api/src/judge/eval/` に、ケース（`cases.ts`）・採点（`score.ts`）・ランナー（`run.ts`）を置く。ランナーは `GeminiInputJudge` を直接作って呼ぶ。

| 項目 | 決めたこと |
| --- | --- |
| ケース | TypeScript の配列。種類（`classification` / `verdict` / `rescue` / `injection`）・単語の id・入力・期待値・任意の Q&A 履歴を持つ |
| 採点 | 種類ごとの正答率。`injection` は 100%、それ以外は 90% で合格 |
| 実行 | `pnpm eval`。`tsx` で動かし、api のビルドには含めない |
| 上限への対処 | 呼び出しの間を 6.5 秒あける。1 分あたりの上限で断られたら `Retry-After` だけ待って送り直し、1 日あたりの上限なら打ち切る |
| CI | 判定のコード・単語のデータ・正規化マッチ・ワークフローを変える PR と、毎晩 03:00（日本時間）。キーは eval 専用の `GEMINI_API_KEY_TEST` |
| 結果 | ケースごとの成否と種類ごとの正答率を標準出力に、CI では同じ内容をジョブの概要に Markdown の表で書く |

## 検討した選択肢

### promptfoo などの LLM の eval ツールを使う

ケースを YAML に書き、プロバイダーを呼んで採点し、結果を Web の画面で見られる。モデルの比較や結果の履歴も持つ。

一方で、ツールがプロンプトを組み立てて Gemini を呼ぶため、本番の `buildJudgePrompt`・structured output のスキーマ・`parseJudgement` の検証を通らない（要件 1）。通すには、ツールから api のコードを呼ぶカスタムプロバイダーを書くことになり、ランナーを自前で書くのと手間が変わらない。依存も 1 つ増える。

### Vitest のテストとして書く

`pnpm test` と同じ仕組みで流せ、成否の表示も揃う。

1 件ずつの合否で落ちるため、種類ごとの正答率で合否を決められない（要件 5）。`pnpm test` から外す設定と、間隔をあけて呼ぶ仕組みも別に要る。

### 全 PR で流す

判定に関わらない変更でも精度の低下に気づける。

60 件で約 6 分半かかり、無料枠の 1 日あたりの上限も食う。AI の揺れで、判定に関わらない PR が落ちることもある（要件 3）。毎晩の全件実行で、判定のコード以外の変更による低下も 1 日以内に気づける。

### 1 件の外れも許さない

精度の低下を最も早く見つけられる。

`temperature: 0` でも判定は揺れ、CI が理由なく落ちる。落ちることに慣れると、本当の低下を見逃す（要件 5）。インジェクションだけは、1 件の外れが答えの漏えいかクリアの横取りにつながるため、全件を要る。

## 影響

- プロンプトやモデルを変えたとき、本番と同じ経路の正答率を種類ごとに比べられる
- ケースはコードと同じリポジトリで型つきで管理し、単語の id の誤りや、正規化マッチで決まってしまう救済のケースをユニットテストで見つける
- 毎晩の実行はデフォルトブランチのコードで流れる。統合ブランチ（`develop`）だけにある変更は、PR の実行か手動の実行で測る
- 結果の履歴は残さない。正答率の推移を追いたくなったら、CI の結果を保存する仕組みを足す

## 見直しの条件

- ケースが増え、無料枠の上限の中で全件を流しきれなくなった場合。有料枠のキーにするか、毎晩の対象を絞る
- 複数のモデルやプロンプトの案を並べて比べる機会が増えた場合。比較の画面を持つツールを検討する
