# 0007. 進行中ゲームを Supabase の PostgreSQL に保持する

## ステータス

採用（2026-10-24）

## コンテキスト

進行中ゲームは `GameStore` インターフェースの裏に置き、API のほかのコードは保存先を知らない（[ADR 0003](0003-game-session-store.md)）。この ADR は、その裏の保存先を決める。

デプロイ先の Vercel（Fluid Compute）では、関数のインスタンスが負荷に応じて複数立ち、使われないインスタンスは停止する。ゲームを始めたインスタンスと、次の入力を受けるインスタンスは同じとは限らない。

保存先への読み書きは次のとおり。

| 操作 | 読み書き |
| --- | --- |
| ゲーム開始 | 1 件作る |
| 入力・ヒント・ギブアップ | 1 件読み、1 件書く。最後の操作の時刻を更新する |
| 期限 | 最後の操作から 1 時間で破棄し、以降は `game_not_found` を返す |

1 件の中身は、単語の id・`locale`・開示済みヒントの数・Q&A 履歴・終了状態と結果である。Q&A 履歴は入力のたびに伸びる。

DB には、出題する単語を置く Supabase の PostgreSQL がすでにある。api は Prisma で読み、ローカルと CI は Supabase CLI で同じ構成の DB を立てる（[ADR 0005](0005-supabase-cli-for-local-and-ci-db.md)）。

満たすべき要件は 3 つある。

1. **どのインスタンスからも同じゲームを読み書きできる**
2. **最後の操作から 1 時間で期限が切れる** — 操作のたびに期限が延びる
3. **ローカル・CI・Vercel で同じ保存先を通る** — 保存先に依存する不具合を、デプロイの前に見つけられる

## 決定

Supabase の PostgreSQL に `games` テーブルを置き、Prisma で読み書きする `PrismaGameStore` を `GameStore` の実装にする。

| 列 | 型 | 中身 |
| --- | --- | --- |
| `id` | uuid | ゲームの id |
| `word_id` | text | 出題した単語。`words` への外部キー |
| `locale` | enum（`ja` / `en`） | 設問・ヒント・定義を返す言語 |
| `hints_revealed` | integer | 開示済みヒントの数 |
| `history` | jsonb | Q&A 履歴 |
| `result` | jsonb（null 可） | 終了したゲームの結果 |
| `expires_at` | timestamp（索引つき） | 最後の操作から 1 時間後 |

ゲームの間に伸びる Q&A 履歴と結果は、行を分けず jsonb に置く。読み出した jsonb は `packages/shared` のスキーマで検証する。

| 操作 | クエリ |
| --- | --- |
| `get` | `id` と `expires_at > 現在` で絞って `expires_at` を 1 時間先へ更新し、更新した行を返す（`updateManyAndReturn`） |
| `create` | 期限切れの行を消し、新しい行を作る（1 つのトランザクション） |
| `save` | 行を上書きし、`expires_at` を 1 時間先へ更新する（`upsert`） |

- 期限内かの判定と期限の延長を 1 つの UPDATE で行う。読み出しと延長の間に期限が切れる隙間がない
- 期限切れの行は、新しいゲームを作るたびに消す。読み出しは `expires_at` で絞るため、消す前の行がゲームとして返ることはない
- 同じゲームへの書き込みが重なったときは、後に書いた方が残る
- `games` はポリシーなしで RLS を有効にする。Supabase は `public` スキーマのテーブルを Data API で公開し、publishable key を持つ誰でも読み書きできる。秘密の単語と Q&A 履歴を api の外に出さず、書き換えもさせない。api はテーブルの所有者のロールで接続するため、RLS の対象にならない
- api はローカル開発・E2E・Vercel のすべてで `PrismaGameStore` を使う。メモリ内の `MemoryGameStore` は、DB を使わないユニットテストと HTTP のテストに差し込む
- レートリミットのカウンタ（`docs/specifications/api.md`「レートリミット」）も、同じ PostgreSQL に置く

## 検討した選択肢

### Redis（Vercel Marketplace の Upstash など）

キーごとの TTL が組み込みで、期限の管理を自前で書かずに済む。読み書きも PostgreSQL より速い。

一方で、保存先が 1 つ増える。Vercel Marketplace の連携と接続先の環境変数が要り、要件 3 を満たすにはローカルと CI にも Redis を立てる必要がある。入力の応答時間は、#28 以降は AI の呼び出し（秒単位）が占めるため、読み書きの速さの差は応答時間にほとんど表れない。

### Supabase の PostgreSQL（採用）

単語と同じ DB に置くため、新しいサービス・環境変数・ローカルのコンテナが要らない。ローカルと CI は単語の取得のために立てている DB をそのまま使い、要件 3 を構成を増やさずに満たす。

TTL は組み込みでないため、`expires_at` 列で期限を持ち、期限切れの行を自前で消す。

### 期限切れの行を定期実行で消す

Vercel Cron や Supabase の `pg_cron` で、期限切れの行を定期的に消す。リクエストの処理に削除が入らない。

定期実行の設定が増え、ローカルと CI では動かない。作成のたびに消す方式でも、削除は `expires_at` の索引で期限切れの行だけを引くため、1 回あたりの負荷は前回の作成からあとに期限が切れた行の数で決まり、テーブル全体の大きさには比例しない。

### 楽観ロックで同時の書き込みを検出する

`version` 列を持ち、読んだときの版と書くときの版が違えば書き込みを拒む。二重送信で Q&A 履歴の 1 件が消えることを防げる。

競合したときの応答（409 を返すか、やり直すか）の仕様が増える。やり直す場合は、AI の判定（#28）をもう一度呼ぶ費用がかかる。画面は送信中に入力を塞ぐため、同じゲームへの書き込みが重なることは通常ない。

## 影響

### 得たもの

- 別のインスタンスに届いた入力でも、同じゲームを続けられる
- api を再起動しても、進行中のゲームが消えない
- ローカル開発・CI・Vercel が同じ保存先を通り、保存先を足すための構成変更がない

### 引き受けたコスト

- 入力・ヒント・ギブアップのたびに、DB への読み書きが 2 往復ずつ増える
- 期限切れの行は、次に誰かがゲームを始めるまでテーブルに残る
- 同じゲームへの書き込みが重なると、先に書いた方の変更が失われる
- 単語の行を消すと、その単語で進行中のゲームも外部キーで消え、`game_not_found` になる

## 見直しの条件

- 保存先の読み書きが、入力の応答時間の大半を占めるようになったとき（Redis を再検討する）
- 二重送信や並行する操作で、Q&A 履歴の欠けが実際に問題になったとき（楽観ロックを再検討する）
- 認証と戦績の保存を入れるとき。終了したゲームを戦績として残すかを、このテーブルの扱いと合わせて検討する
